# ARM64 obfus.h feasibility — instruction-level POC (not a port)

**Status:** isolated source-only experiment for `qigao/tcc`. Nothing in this folder is a replacement for `DosX-dev/obfus.h`; no production-facing headers or TinyCC binaries are modified. Never silently disable protection when unsupported.

## Evidence and scope

- `DosX-dev/TinyCC-builder` offers `arm64-win32-tcc.exe`; it **compile-tests** ARM64 but does not claim ARM64 runtime for the `obfus.h` integration.
- The upstream `DosX-dev/obfus.h` header has 23 numbered sections and x86/x64-specific instruction strings (e.g. EAX/ESP, encoded `0xE8`/`0xE9` branches, stack proxy frames) and Windows x64 `.pdata` decoys. Replacing its architecture preprocessor branches is **not** enough.
- Pinned TinyCC `mob` commit `e23dabed154a8495f3ac1ff3cc9d04fa1c207893` includes `arm64-asm.c`, whose assembler supports GCC-style extended asm, `eor`, `add`, `sub`, `b`, conditional branches, `%w` registers and constraints. These are suitable seams for safe ARM64-specific lowering.

This POC includes 32-bit modulo arithmetic, two seed-selected reversible instruction sequences, **A64-computed equality predicates**, and build-time encoded string bytes reconstructed into caller-owned memory. The next gate adds **64-bit borrowed object-pointer token encode/decode** (without ownership transfer or dereferencing an encoded token) and C-baseline differential tests covering switch, break/continue, multiple returns, side effects and wrapping unsigned values. Both seed variants must produce identical semantics while producing different binaries; a wrong seed/fixture pair must fail compilation. No compiler flags may select a silent no-op fallback. Unknown upstream `OBFH_*` feature flags and legacy `NO_*`/`CFLOW_V2`/`VIRT` options now fail compilation rather than being silently ignored; the 32-bit seed range is also enforced.

**Explicitly unsupported:** complete upstream `obfus.h` macros and automatic keyword rewriting; native x86 call/return/stack proxies; `HIDE_STRING(str)` source compatibility; VM dispatcher virtualization; anti-debugging, trap instructions, fake sections, Windows unwind metadata, CFG, BTI/PAC, signed binaries, and ARM32. The small test is **not** a measure of resistance to reverse engineering. Seed values are public layout selectors, not cryptographic keys. Never use this demo to protect real secrets.

## First public source-signature slice: bitwise `VM_*`

`obfh_arm64_vm_bits.h` is an **opt-in** header separate from the original `DosX-dev/obfus.h`. It exposes exactly six source-compatible macro signatures: `VM_AND`, `VM_OR`, `VM_XOR`, `VM_NOT`, `VM_SHL`, `VM_SHR`. They return `unsigned int`, evaluate each operand once, implement 32-bit unsigned bit patterns, and mask variable shift counts modulo 32 to match upstream region 14. Their bodies use genuine AArch64 `AND/ORR/EOR/LSL/LSR` instructions; `VM_AND` also has two seed-selected reversible instruction sequences.

This is **source-level/semantic parity only**. Upstream's `VM_*` macros route via an encoded VM instruction program, whereas this experimental implementation executes ISA operations directly. It must not be described as VM virtualization, full binary obfuscation parity, or a replacement for the original header. All other `VM_*` names, automatic keyword interception and full `HIDE_STRING(str)` remain unported and unexposed.

`vm_bits.c` is a separate native executable that reproduces upstream [`tests/vm.c`](https://github.com/DosX-dev/obfus.h/blob/main/tests/vm.c)'s bitwise type, evaluation-count and shift semantics. It tests 49 boundary-value pairs, 4,000 deterministic pseudo-random pairs, nested calls and side effects. Linux native GCC/Clang/TinyCC and real Windows ARM64 compile and execute both seed variants; Windows checks `0xAA64` and exact SHA-256 before running.
## Explicit `VM_IF` / `VM_ELSE_IF` / `VM_ELSE` source-signature slice

`obfh_arm64_vm_branches.h` separately exports three original explicit branch macro signatures. Boolean normalization uses `!!(condition)` exactly once, followed by A64 equality/value transport. The `VM_ELSE` form deliberately remains `else if (true)` like the upstream region-14 contract so nested dangling-else behavior is not altered.

`vm_branches.c` follows the logic of upstream [`tests/vm_branches.c`](https://github.com/DosX-dev/obfus.h/blob/main/tests/vm_branches.c): it checks short-circuit side effects, nested `if/else`, 64-bit integer and pointer truth, floating NaN/infinity/signed zero, `goto`, `break/continue`, 1,000 randomized branch chains and 32 recursive cases against unprotected C baselines. This is an **explicit macro** port, not automatic rewriting of C's `if` tokens or the original encoded VM program. The header may be opted into independently; it must never silently claim unsupported upstream features.
## First bounded encoded VM program (W2 experiment)

`obfh_arm64_vm32_program.h` adds a **separate, opt-in real instruction stream interpreter**. Each `VM_AND/OR/XOR/NOT/SHL/SHR` source site owns four immutable, seed/site-encoded 32-bit words: `LOAD_A`, `LOAD_B`, selected `ALU`, `RETURN`. The decoder uses genuine A64 `EOR`, then validates all four decoded words and dispatches actual A64 `AND/ORR/EOR/LSL/LSR` operations. Runtime execution returns an explicit four-step receipt. This is not a C arithmetic fallback, and it does not use W+X memory or rewrite frames.

The executor is **fail closed and transactional**: null operands/output, incorrect program length, reserved bits, invalid opcode/register/return, wrong operation, or mismatched key return a named error without changing the caller-owned result/step receipt. The `VM_*` macros cannot return an error, so malformed encoded programs abort rather than silently computing a plain C result. All input expressions are evaluated once and bitwise results retain `unsigned int` with modulo-32 shifts.

`vm_program.c` verifies 49 boundary pairs, 4,000 deterministic pairs, nested public calls, side-effect counts, decode/dispatch step receipts and negative corrupt-word cases. It builds independently from `obfh_arm64_vm_bits.h`; the earlier direct A64 implementation is an **isolated diagnostic comparison**, not an automatic fallback. CI includes both executables so one cannot silently replace the other. The Windows native gate now requires eight PE variants (four fixture groups × two seeds), each executed ten times with `0xAA64` and SHA-256 validation.

**Remaining gaps:** this compact four-word 32-bit bitwise VM uses a *new experimental format*, not upstream's encoded layout, nonces, mixed integer/floating values, jumps, VM program variants or API call interception. No statement of complete upstream `Obfh_VirtualMachine` compatibility, automatic CFLOW, cryptographic protection or qualified Release is warranted. Next gate is a differential port of upstream bytecode shapes and error semantics with exact instruction-count and bounds proof.
## Bounded encoded VM32 control-flow extension (W2)

`obfh_arm64_vm32_codec.h` is now the **single** VM32 seed/site encoder, key and opcode owner shared by the existing fixed four-word bitwise executor and the new control-flow interpreter. The two experimental executors are separately called for differential qualification; neither is an automatic fallback for the other.

`obfh_arm64_vm32_flow.h` adds decoded `TEST`, conditional `JFLAG`, unconditional `JUMP`, and one-register unsigned `DEC` to a compact **new** experimental VM format. It executes decoded words through A64 `EOR/ORR/AND/SUB/...` register instructions. The interpreter admits 4–16 encoded words and a caller-provided instruction budget from 1–128; out-of-range targets, jumps into the two-word input prologue, malformed opcode/register/immediate bits and absent terminal RETURN are rejected before execution. Runtime use of an uninitialized register or flag fails rather than reading guessed state.

Validation first, execution second: **any failure leaves both caller-owned output and executed-step receipt unchanged**, even if a loop has already executed many steps. This is a transactional caller-visible contract, not protection against crashes or a security sandbox. It never writes executable memory, changes SP/LR or runs alternate engines. On success it returns the executed instruction count, not merely the encoded length; backward loops terminate through `max_steps`.

`vm_flow.c` checks 4,096 deterministic conditional branch pairs against C, both branch paths and exact execution counts, count-down loop budgets (including exact/admissible and one-less/rejected), unsigned-zero underflow loops, invalid/misaligned branches, wrong seed, reserved and invalid words, uninitialized register/flag, NULL arguments, and budget overflow. Each negative case checks the sentinel output and step receipt. The original VM32 bitwise and source-macro fixtures remain independent and green-only on the exact PR HEAD. CI builds this added executable with GCC/Clang/TinyCC native AArch64 plus the hash-verified Windows cross-build and genuine Windows ARM64 runner, bringing the matrix to **10 executables (5 program groups × 2 seeds), 10 real native repetitions each**.

This extension is still **not** the upstream `obfus.h` encoded VM format: upstream has a richer opcode permutation, flags and long-double register layout, and distinct branch semantics. Support is confined to the explicitly documented POC instruction subset; the Release gate remains closed.
## Exact upstream packed-word encoder/decoder qualification (region 11/14)

`obfh_arm64_upstream_codec.h` is a **separate, purely 32-bit C11** port of the original obfus.h packed-word encoding/decoding formulas, anchored to upstream Git blob `4c06fbc06f907afb3989e2851bed7583cfd0b6b0` (rather than a moving branch). It includes all **6 opcode transforms**, all **9 word mask/encode transforms**, all **6 D/A/B field permutations**, all **4 packed field layouts**, plus the key-dependent rotation and the 3-round modular inverse for odd opcode multipliers. C11 is sufficient here: upstream encodes 32-bit words arithmetically, without an x86-specific instruction requirement. The existing VM32 encoder remains the only owner of the *separate POC* VM32 format; do not silently conflate or substitute the two wire formats.

`vm_upstream_codec.c` compares every output to an independently expressed copy of upstream `OBFH_V_INSTRUCTION`/`OBFH_V_PACK`/`OBFH_V_ENCODE_RAW` semantics and verifies decode roundtrips. It exhaustively covers 6×9×6×4 = **1,296 mode combinations**, each with eight opcode/register/immediate/PC vectors (**10,368 encoded words**). A separately computed, fixed 64-bit FNV-1a golden digest `b19831d024873da0` protects against comparing two identically incorrect encoders. Invalid pointer, PC, immediate, opcode and register inputs fail without overwriting output.

This is an **exact packed-word codec contract**, not the full original `Obfh_VirtualMachine` implementation. Every bit in the 32-bit instruction is used, so arbitrary bit flips and wrong keys still decode to *some* tuple; the encoding is not authenticated and corrupt programs require independent opcode, operands and execution-flow validation. The upstream 4-register long-double runtime, nonce handling, flags, VM program templates, keyword interception, exception/CFG/unwind and downstream Release qualification remain open. The codec test is an extra native executable for Linux GCC/Clang/TinyCC and Windows TinyCC, raising the Windows native matrix to **12 PE variants × 10 runs** without creating a second CI workflow.
## First original-format packed bitwise interpreter (experimental)

`obfh_arm64_upstream_vm_bits.h` reads the **original obfus.h 32-bit packed WORD format** through the exact codec and recognizes the **actual upstream numeric opcodes** `LOAD_A=1`, `LOAD_B=2`, `BAND/BOR/BXOR/BNOT/BSHL/BSHR=18..23`, `RETURN=26`. The **four-instruction subset** has an explicit operand schedule (`R0` input A, `R1` input B, `R2` result), a 4-step execution receipt, and actual AArch64 ALU instructions. The interpreter prevalidates **all four decoded words** before modifying output; unknown opcode, invalid register layout, unexpected operation, bad length or step budget fails closed.

`vm_upstream_exec.c` constructs the four encoded instruction words using the verified upstream codec, then executes the real packed bitwise subset for **all 1,296 mode combinations × six bitwise operations × seven data pairs = 54,432 native semantic cases**. Additional tests corrupt instruction words or use invalid keys/budgets, and verify caller-owned result/receipt remain unchanged. The build seed is observed through a volatile input so the two compiled PE variants are independently distinguishable. This test is separate from the POC VM32 program/flow tests; they are **not** silent fallback alternatives for a production API.

**Scope limit:** the original obfus.h VM stores typed operands as encoded `long double` bytes with control registers, random nonces, packed program variants and richer flag/jump semantics. This first original-format interpreter intentionally handles only 32-bit unsigned bitwise operands and a fixed 4-word schedule. It builds the test instruction stream at runtime instead of claiming the original source-level immutable per-site `OBFH_V_PROGRAM` templates have been ported. No full source-API compatibility, Windows unwind/CFG proof or Release admission is implied. The Windows ARM64 native acceptance matrix now includes **14 distinct PE variants × 10 executions each**, contingent on the exact-HEAD CI.
## Original VM operand object-byte transport (region 09; experimental)

`obfh_arm64_upstream_value.h` ports the original `OBFH_VM_VALUE` **object-byte transport**, preserving the full `sizeof(long double)` representation rather than converting operands through `double`. Each packet carries caller-owned `bytes[sizeof(long double)]`, a 0/1 `floating` tag and the original `nonce = (floating_nonce >> 1) ^ seed`. The original seed-selected byte transform (`XOR+ADD` vs `ADD+XOR`), four xorshift maps (seed bits 21–22), rotation, byte permutation and source salt range 16..48 are reproduced arithmetically in C11. The original `obfh_int_proxy`/`obfh_double_proxy`/`obfh_condition_proxy` return identity for these integer salts; this POC does not implement or silently bypass their control-flow/stack obfuscation.

`vm_upstream_value.c` compares two separate encoding paths, executes all eight byte-transport mode combinations, checks exact decoded object bytes including raw patterns and sample `long double` values (positive/negative zero, fractional and negative values), varies the nonce without changing the underlying bytes, and enforces transactional rejection on invalid size, salt, floating tag and null arguments. Independent golden digests lock the 128 mode/sample/tag vectors for both supported native object sizes: **8 bytes → `4334f9046441f6b9`; 16 bytes → `a948b84150edced9`**. The test rejects other `long double` sizes rather than guessing layout or silently converting precision. A reversible byte codec is *not* authenticated encryption; a wrong key/salt can produce different bytes without a reliable detectable error.

This step concerns the **input operand transport** only, not upstream VM register masks, numeric register layout, opcode flags, per-site program templates, or full `long double` arithmetic acceptance. The packet format is a source-faithful study of the upstream transport, not a new general-purpose or persisted wire protocol. No new workflow was added: it runs under the existing GCC/Clang/TinyCC Linux ARM64 and hash-verified Windows ARM64 acceptance matrix, now with 16 executable variants × 10 native executions on Windows.
## Original VM four-register, flags and control storage (region 11; experimental)

`obfh_arm64_upstream_registers.h` ports the *semantic storage transformations* from the original `OBFH_V_REGISTER` and `OBFH_V_CONTEXT` to an isolated four-slot model. Each long-double-sized register stores its encoded bytes plus the original **per-write mask** derived from `key ^ (register*3266489917) ^ steps`, the seed-selected `OBFH_MIX_FIELDS` transform, 3 reversible byte modes and forward/reverse byte traversal. Reads use the **stored mask**, so a later step-count change must not invalidate previously written values. COPY/SWAP operate on encoded storage without numeric conversion. Invalid or uninitialized register access rejects without partial caller-visible writes.

Flags use the original seed-selected XOR/ADD/SUB storage and derived flag-key, separately from the `flags_ready` latch. Control registers use seed-selected XOR-vs-ADD address masks. `CADD` sign-extends its 18-bit immediate and updates the CONTROL flag; `CXOR` operates directly on the encoded control word, and `CROL` rotates the decoded control by `(imm % 31) + 1`. These tests do not claim complete VM compare/boolean/jump behavior or safe execution of arbitrary source bytecode.

`vm_upstream_registers.c` uses the full shifted-seed expression `(seed >> 8) % 3` (not simply the two low mode bits); this is checked independently across all generated profiles. The original compact reference test was corrected after TinyCC exposed its mistaken mode-index assumption; the actual register implementation was not relaxed. The test validates 3 observed byte modes (`(seed >> 8) % 3`) × 2 traversal directions × 8 seed draws = **48 combined state profiles**, 4 registers, independent oracle bytes/masks/flags/control storage, and exact native golden receipts for 8-byte (`11d5cfdd0648db80`) and 16-byte (`b1e56bb008e20fa6`) `long double`. It also tests initialized-mask ownership, read-after-step-change, copy/swap, signed CADD, XOR/rotate controls, and transactional negative cases. All `long double` object bytes remain opaque; the **physical seed-permuted layout** of the upstream `OBFH_V_CONTEXT`, full floating-point VM arithmetic, and upstream `OBFH_V_PROGRAM` templates still require separate porting and validation. This test joins the existing Linux/Windows ARM64 CI as the **18th** per-seed executable variant set (18 PE files total across two seeds), with no added consumer project or CI workflow.
## Integrated original-format VM runtime (all eight upstream templates)

`obfh_arm64_upstream_runtime.h` combines the previously qualified **original packed-word decoder**, `OBFH_VM_VALUE` object-byte/nonce transport, encoded `long double` four-register state, flags/control masks and AArch64 register ALU into **one bounded interpreter**. This is a genuine decoded instruction owner, not a new C-fallback entrypoint. It admits original opcode numbers `LOAD_A/B`, `LOAD_PAIR`, `MOVE`, `SWAP`, `COPY_RETURN`, `RETURN`, `ADD/SUB/MUL/DIV/MOD`, `COMPARE/BOOLEAN/TEST`, `CADD/CXOR/CROL`, `JUMP/JFLAG`, and six bitwise ALUs. The original VM implements numeric arithmetic in C; the ARM64-specific bitwise ops use real A64 assembly. No SP/LR manipulation, W+X executable buffers or alternate VM fallback.

`vm_upstream_runtime.c` reproduces the **actual instruction shapes of all eight upstream `OBFH_V_PROGRAM_0..7` templates** using the exact source-format codec, one original-operation mapping (`0..18`) and one execution state. It checks results against ordinary C for all 19 operation selectors, float/non-float modes, signed zero, NaN/infinity comparisons and integer division/modulo corner cases. It also compares the executed PC trace and step count: **variants 0 and 1 use 4 and 6 steps**, variants 2–5 exercise different TRUE/non-TRUE branch topologies, variant 6 exercises CONTROL-flag convergence, and variant 7 exercises key-selected register/control preparation and a result-dependent second branch. Inputs are encoded using two independently salted `OBFH_VM_VALUE` packets; numerics live in the original masked register slots. Tests inject malformed original instructions, uninitialized register, wrong Boolean immediate, bad jump, zero/over budget and out-of-range numeric cast, asserting caller-owned output/trace/step receipt is unchanged on error.

**Explicit remaining differences:** the builder generates the source-equivalent instruction words for all eight templates at runtime; it does not yet implement their compile-time immutable call-site emission or prove binary-identical upstream code generation. The original `OBFH_V_CONTEXT` physical seed-permuted layout, process-exit failure policy, upstream anti-debug/stack proxies and API/CRT interception remain unported. FP object representation is verified for native `sizeof(long double)` 8/16; cross-platform binary ABI and advanced unwind/CFG are not proven. Unsupported numeric conversions fail closed instead of invoking undefined C casts. This integration **is not complete upstream `obfus.h` support** or authorization for product Release.
## Compile-time immutable per-site original VM instruction streams (W2)

`obfh_arm64_upstream_static.h` is the first **explicit-declaration** static instruction emitter for the original 8 packed program shapes. Every `OBFH_SC_DECLARE_0..7(name, seed, key, operation)` invocation creates one **file-scope `static const uint32_t name_words[N]`**, using only C integral constant expressions. The original 4/6/11/10/12/11/8/15 lengths, original source opcodes, fields, packed layouts, seed-controlled opcode/word masks, and key-controlled instruction rotation are fixed at compilation, **not encoded at runtime**. The key's source variant bits 24..26 and operation range are checked with `_Static_assert`; a wrong variant must fail to compile.

`obfh_arm64_upstream_program_reference.h` is now the **single reference owner** for all eight original template instruction shapes and the normal-C numeric/branch/PC-trace oracle. It is a test helper, **not a second VM**. `vm_upstream_static.c` declares ten distinct sites (all eight variants plus two separate sites with the same variant and different keys/layouts), compares **every stored encoded 32-bit word** to that independent source-shaped builder, runs through the already accepted integrated `obfh_arm64_upstream_execute`, checks six inputs per site with semantic and exact PC/opcode traces, verifies input expressions evaluate exactly once, and hashes the immutable program before/after execution. The existing CI also compiles a deliberately inconsistent variant under GCC/Clang/TinyCC and must see the expected `_Static_assert` failure.

**What this does not yet claim:** this is an explicitly named site declaration, not the upstream automatic `OBFH_VM_EXEC`/`VM_*` macros (including compiler `__COUNTER__` key derivation, `OBFH_JUNK_WORD` and source-position entropy). The public expression must retain file-scope `__typeof__` compatibility, so a bare GNU statement-expression is not a valid replacement. The emitted arrays are compiler `static const` objects but binary section flags, PE relocation behavior, the original physical `OBFH_V_CONTEXT` layout and ABI/unwind remain separate gates. This is a deterministic compatibility and reproducibility test, **not proof of obfuscation strength or product Release eligibility**. On an exact-HEAD green CI, Windows ARM64 will test 22 PE variants with ten native executions each.
## Exact four physical `OBFH_V_CONTEXT` layouts (ABI-gated study)

`obfh_arm64_upstream_context.h` now declares four **unpacked C physical structs** whose member orders match upstream source blob `4c06fbc0`: the location of `registers[4]`, `controls[4]`, `result`, and all eight 32-bit status/flag/key/counter fields is selected by `(OBFH_SEED >> 4) % 4`. `obfh_upcontext_selected` is a compile-time typedef of the matching physical struct. These declarations intentionally preserve the compiler's native alignment and padding instead of applying `#pragma pack`, changing register slot sizes or converting the `long double` result to `double`.

`vm_upstream_context.c` independently calculates the **expected field offsets and complete structure size from the upstream member order, each member's size and C alignment**, then checks `offsetof`, `_Alignof` and `sizeof` for **all four layouts in each native executable**. It tests transfers between the already qualified semantic VM state and each physical representation, preserving every encoded register byte/mask, flags, control words, program counter/status and the raw result object bytes. It verifies reads after a step-counter change and rejects invalid export/import arguments without writing caller-owned state. These are ABI layout and state-transport tests, not a second VM engine.

**Earlier milestone:** the integrated interpreter originally used a durable semantic context and separately tested physical layouts. The newer live-context integration section now makes the source physical layout authoritative between VM instructions. Test success does not yet imply full original Windows entrypoint/callback ABI, stack/unwind, PE relocation/layout or public `VM_*` caller macro compatibility. Existing compilation with `OBFH_SEED=0x12345678/79` selects layout 3, but each binary also checks layouts 0–3 independently; no extra installer, consumer project or CI workflow has been introduced. When accepted, Windows ARM64 runs 24 PE variants × 10 native repetitions.
## Automatically keyed named VM sites (original counter and junk-word formula)

`obfh_arm64_upstream_auto_site.h` reproduces the original `OBFH_VM_EXEC` source key expression's unsigned operations: `__obfh_vsite = __COUNTER__`, the **three following `OBFH_DRAW16` counter draws**, source `__LINE__`, `OBFH_JUNK_WORD`, and `OBFH_MIX_A`. Three counters (rather than six) are consumed because C preprocessor arguments are expanded before duplicated substitution; this was independently checked against the original macro definitions. An `OBFH_AS_DECLARE(name, operation)` invocation captures its counters once, derives the key in C integral constant expressions, and emits a different file-scope **`static const` program** with the original eight possible instruction patterns selected by key bits. No runtime bytecode construction or alternate VM execution path is introduced.

**At the earlier auto-key milestone**, the source site used a 15-word padded array with an exact logical length. The later compact-array section documents its replacement with eight exact-size array types and separate file-/block-scope storage rules; no runtime bytecode construction or second VM was introduced.

`vm_upstream_auto_site.c` declares four independently keyed source sites, checks counter consumption, verifies the key against a separately written C implementation of the original draw/junk/mix formulas, compares **every executable word** with the single source-shaped template reference, requires zero tail words, and differentially executes through `obfh_sc_call`/`obfh_arm64_upstream_execute` with exact PC/opcode routes and one-time argument evaluation. `__typeof__` at file scope remains valid for the typed function-call wrapper. This is still a **named-site declaration**, not the original automatic value-returning public `VM_ADD`/`VM_AND` macros; no full source compatibility or protection strength is claimed.
## Original-spelling `VM_*` source expression adapter (experimental)

`obfh_arm64_upstream_vm_public.h` is an **opt-in prototype of the original value-returning VM source macros**: integer arithmetic and comparisons, unsigned bitwise operations, double-input operators, `VM_OBF_INT`/`VM_OBF_DBL`, and explicit `VM_IF` / `VM_ELSE_IF` / `VM_ELSE`. It uses the original GNU statement-expression form and therefore remains an *inside-function* expression API, as in the upstream source. Each macro captures its own `__COUNTER__`/line-derived key through `OBFH_AS_DECLARE`, emits source-encoded `static const` instructions, then invokes the **same single integrated original-format runtime**. Invalid execution invokes `abort()`; no plain-C arithmetic fallback is permitted.

The initial `vm_upstream_public.c` native suite exercises original spelling directly (`VM_ADD`, `VM_SUB`, `VM_MUL`, `VM_DIV`, `VM_MOD`, signed/unsigned comparisons, `VM_AND/OR/XOR/NOT/SHL/SHR`, `_DBL`, ID, nested VM calls and branch chains). It tests output values, side-effect counts, short-circuit behavior and actual Windows ARM64 execution. This reuses the existing workflow with two build seeds and strict `-Werror`, bringing Windows admission to **28 PE variants × 10 native executions** only after exact-HEAD CI is green.

**Not a finished drop-in header:** this prototype does not yet reproduce at that earlier HEAD, operand RND nonces and compact code had not been implemented; newer sections record the source nonce and exact array-length candidates. No automatic C token/keyword interception, `HIDE_STRING`, stack/call/return proxy, anti-debug, fake PE sections or Windows unwind/CFG/BTI/PAC gate has passed; the production Release policy remains denied.
## Independent upstream operand nonce draws (source counter ABI)

Original `OBFH_VM_OPERAND(value, salt, floating)` computes the operand nonce using `RND(1,2147483647u)` for **each of the two operands**. `RND` is a **compile-time** `__COUNTER__`/`__LINE__`/`OBFH_SEED` integer expression (not a runtime PRNG). Because the program-site key consumes its own site counter plus three JUNK_WORD draws, the first operand uses the **next counter** and the second uses the **following** counter. The previous POC's `site ^ key` and `nonce + 7` shortcut was suitable for differential fixture data but was **not** an exact source-operand generation rule.

`obfh_arm64_upstream_auto_site.h` now exposes `OBFH_AS_RND31` and `OBFH_AS_DECLARE_NONCES(name)` with the exact 32-bit unsigned arithmetic and modulo-2,147,483,647 range, and compile-time checks that the two counters are consecutive. The public expression adapter calls the same original-format VM using `obfh_sc_call_nonces` with **two distinct per-site nonce inputs**, not an inferred second operand nonce. The old explicit `obfh_sc_call` fixture API remains a forwarding adapter to the same execution engine for earlier tests; neither interface adds a plaintext operation fallback.

The nonce macro explicitly masks the compiler's 64-bit constant-folded product to 32 bits **before the range modulo**. This is required because Windows TinyCC initially widened the intermediate product while Linux GCC/Clang/TinyCC already matched upstream; four fixed golden `_Static_assert`s prevent this cross-toolchain regression.

`vm_upstream_nonce.c` independently transcribes the source formula, checks four named sites and all six original counter draws per site, packet nonce/floating fields and distinct encoded bytes, runs the integrated VM to check values and exact PC traces, and rejects zero/out-of-range nonces without mutating caller-owned output or step receipt. GCC/Clang/TinyCC native Linux ARM64 and SHA-verified Windows ARM64 are included in the existing workflow, raising the matrix to **30 executable variants × 10 native runs** on exact-HEAD acceptance.

**Scope boundary at the earlier nonce milestone:** fixture salts were 17/41; the later header-salt section above adds source-selected 16..48 values to the public adapter, while full original header counter-history parity remains an open integration gate. Other remaining differences include exact source macro side effects, compact per-variant static site size, original process-exit policy, and physical-context runtime wiring. Compile-time nonce entropy should not be described as cryptographic unpredictable runtime randomness.
## Source-selected header `SALT_NUM1/SALT_NUM2` (RND 16..48)

Upstream `obfus.h` declares `typedef enum { SALT_NUM1=RND(16,48), SALT_NUM2=RND(16,48) } VM_SALT` before the VM kernel. These are **two consecutive header-time `__COUNTER__` expansions**, with the same unsigned 32-bit multiply/wrap semantics as operand `RND31`, but modulo **33** and a minimum of **16**. `OBFH_PUB_SALT_NUM1/2` now record the two actual source-header line/counter positions and calculate values using `OBFH_AS_RND_SALT` at compilation. The original full upstream header may have a different preceding counter history and different source line numbers; this is **source-formula parity for this ported header**, not a claim of identical absolute salt values when compiled through a different header.

`obfh_sc_call_profiled` takes both independently generated operand nonces **and both source-selected salts** into the same original packed-VM decoder, with a transactional range gate (`16..48`, nonce `1..2147483647`). The existing explicit `obfh_sc_call_nonces` fixture continues to forward the prior salts `17/41` through that **same** routine so prior acceptance is not lost. The public `VM_*` expression adapter now invokes `OBFH_SC_CALL_PROFILED` with the two source-header salts, and does not use the fixture shortcut.

`vm_upstream_nonce.c` now checks an independent C oracle for both header salt expansions, four fixed `RND(16,48)` golden constants over two build seeds, all original nonce counters, input byte transport and original VM PC traces. Its existing four-site native differential exercises both the historical and source-selected salt profiles. Incorrect salt or nonce values are rejected without changing output/steps/trace. These checks run in the **existing** nonce executable, without a new build target, downstream consumer project or extra CI workflow.

**Remaining:** match the original complete-header counter history and all caller source positions when the real port replaces the original `obfus.h`, PE section/relocation proof for compact arrays, original external physical-context **ABI** proof (live internal physical state now handled separately), original failure policy, protected `VM_ELSE` side effects, `HIDE_STRING`, automatic keywords, stack proxy, Win ARM64 unwind/CFG, and product Release.
## Exact-size original VM program arrays (compact source-site candidate)

`OBFH_AC_PROGRAM(name)` now uses the **upstream-style nested `__builtin_choose_expr`** to select one of eight type-distinct `const uint32_t[N]` compound literals, with **actual array storage lengths `4/6/11/10/12/11/8/15`** and no trailing zero capacity. The instruction expressions are the same original source-program words already accepted by `OBFH_SC_DECLARE_0..7`; `OBFH_AC_ASSERT_LENGTH` proves `sizeof` the selected **array** equals `NAME_length × sizeof(uint32_t)` at C compilation. The single original-format VM, codec and register state are unchanged; there is no new runtime encoder or fallback.

The original eight `OBFH_SC_DECLARE_0..7` declarations remain the **file-scope static const source** for explicitly selected variants, with their exact original element counts. The **automatically keyed** source forms now use `OBFH_AC_DECLARE_META` for file-scope compile-time key/counter metadata and construct their exact-size `const` compound literal **inside the calling function** via `OBFH_AC_PROGRAM`. `OBFH_AC_DECLARE_EXPR` does the same inside the original public `VM_*` GNU statement-expression wrapper. This matches upstream's block-duration compound literal model. **Windows TinyCC rejects file-scope static pointer initialization from `__builtin_choose_expr`** (`initializer element is not constant`); rather than introducing an illegal, platform-specific initializer or padded fallback, only valid C block-duration constructors are used for the automatic form. No 15-word padded data arrays remain in automatic execution.

`vm_upstream_auto_site.c` checks four file-scope keyed metadata sites plus **all eight fixed-key templates**, with their code arrays constructed inside each test function, against the single source-shaped reference builder, verifies actual compile-time array storage size for each, preserves source `__COUNTER__` key derivation, and checks execution/trace and once-only arguments. `vm_upstream_public.c` and `vm_upstream_nonce.c` retain existing source-macro and independent nonce/salt gates with the compact array selector. Native GCC/Clang/TinyCC, real Windows ARM64 and PE provenance remain required before this candidate is admitted.

**Not proven by array-size acceptance:** exact binary section placement/relocation and read-only enforcement on all compilers, direct-field computation without a staging view (physical bytes now own state between instructions), full original header counter history, process failure policy, `HIDE_STRING`, automatic keyword rewriting, stack/call proxies and Windows ARM64 unwind/CFG. A `const` compound literal is a C mutability guarantee, not an executable/PE protection-strength claim.
## Original HIDE_STRING stack lifetime and encoded-literal boundary (W4 candidate)

The upstream `obfus.h` `HIDE_STRING(str)` is **not** a general encrypted-literal API: it constructs `STACK_STRING("\0" str "\0")` (a caller-block-duration compound `char` array) and `obfh_process_hidden_string` returns **that buffer plus one byte**, while other source predicates/junk/timestamp paths are x86-specific. The plaintext `str` literal may remain visible in a PE/ELF even though the runtime pointer points to stack memory. A direct `#define HIDE_STRING(str) (str)` or an unencrypted stack-only shim would be a **false protection claim** and is intentionally NOT provided. Similarly, eshard/obfuscator-llvm globally encrypts IR constants and installs a module constructor to decode global strings; that process lifetime is **not equivalent to this caller-owned stack lifetime**.

`obfh_arm64_upstream_hide_string.h` now provides an explicitly **encoded-fixture-only** `OBFH_HIDE_ENCODED_SITE(array,hash)` call-site macro, backed by the same already qualified ARM64 fixture byte decoder. It uses a C99 `char[sizeof(array)+2]` **caller-scope compound literal**, restores the exact leading NUL / string NUL / trailing sentinel layout, then returns `frame+1`. Caller-owned buffers from distinct expressions remain independent and valid only until the enclosing lexical block ends. The decoder checks capacity, final NUL and a fixed FNV32 receipt. On corrupted ciphertext it clears the entire caller frame through volatile writes and rejects; on invalid arguments it does not modify caller bytes. The caller may explicitly scrub the plaintext after use. No heap, global decode buffer, plaintext-C fallback, W+X code, or new VM is introduced.

The **existing** `generate_fixture.py` now emits three extra ciphertext-only samples into its existing seed-locked generated header: UTF-8 CJK/emoji, embedded NUL, and an empty C string. `smoke.c` validates independent fixed length/hash constants, all source-style sentinel bytes, full byte payloads rather than `strlen`, two simultaneously live caller buffer identities, mutation isolation, caller erasure, corruption wipe, and preflight rejection. The existing `verify_binary.py` can scan multiple UTF-8/hex patterns in one pass; the single ARM64 CI workflow checks that the linked smoke PE/ELF contains **none of the exact fixture plaintext byte sequences**. This is a narrow binary-residual check, **not proof of cryptographic protection or absence of every plaintext fragment/optimized representation**.

**Still blocked:** arbitrary-literal original `HIDE_STRING(str)` source syntax with guaranteed protected output; original `OBFH_HIDE_JUNK`, `obfh_condition_true` and timer branch side effects; full-header counter provenance, compiler string literal rewriting, stack lifetime escapes, multithreaded product ownership, Windows CFG/unwind and Release. A true arbitrary-literal solution needs a verified source/compile-time literal transformer in TinyCC or a separately selected, fully qualified LLVM string pass; never silently swap those two compiler architectures. This W4 candidate does **not** remove the original public API blocker.
## Live original `OBFH_V_CONTEXT` ownership (integration gate)

`obfh_arm64_upstream_context.h` now provides an original physical-context **union of all four native layout variants**, selected by the program seed's `(seed >> 4) % 4`. `obfh_arm64_upstream_execute` has **one interpreter** and stores its authoritative encrypted registers, control words, flags, PC, status, step count and raw `long double` result in the selected physical member **between every decoded instruction**. A single-instruction `obfh_upreg_state` staging view is imported before execution and exported afterward; it cannot remain the durable state across VM steps. Successful RETURN/COPY_RETURN publishes the output/step/trace only after committing to physical storage and reading the committed result back. Failure never publishes partial caller-owned output.

The original source member order, native alignment and padding are unchanged; the preexisting `vm_upstream_context.c` independent `sizeof`/`_Alignof`/`offsetof` tests are retained. Additional native qualification checks all **four physical modes as actual state owners** and verifies PC/status, copy of every masked register/control/flag and raw result, read-after-step-change, bad seed/cookie/mode rejection, and no-write-on-invalid ownership. `vm_upstream_runtime.c` also requires the complete original packed-program differential to execute under **all four runtime physical layouts** rather than accepting a mode supported only by an isolated structure test.

**Precise boundary:** this is an original-layout **durable state owner with a temporary per-instruction staging view**, not a claim that each arithmetic helper directly aliases field offsets. The exported `obfh_upcontext_selected` type stays compiled for the exact build seed; the runtime union permits independent native qualification with other test seeds in one binary. It does not prove external Windows callback ABI, PE section placement, exceptions/unwind/CFG, original process-exit semantics or complete upstream `obfus.h` feature parity. No extra interpreter, fallback, consumer project or CI workflow was created.
## Windows ARM64 PE physical protection and relocation audit (W3 candidate)

`verify_pe_vm_sections.py` uses only the Python standard library to inspect the **actual ARM64 PE32+ (`Machine=0xAA64`)** output of the existing `vm_upstream_static.c` fixture. It independently re-implements original packed-word encodings for **three real program sites**: the four-word `site0`, fifteen-word `site7`, and four-word differently seeded/layouted `site0_second`. It searches for each **complete exact byte sequence**, checks native word alignment, requires unique placement in a readable, **non-writable and non-executable PE section**, and rejects W+X sections. If base relocation entries exist, it checks their RVA mapping and fails if an entry could overlap the protected code array bytes.

This is a *real binary artifact* qualification instead of relying on `static const` source qualifiers, C `sizeof`, or PE machine header alone. The existing Windows x64→ARM64 TinyCC cross-build runs the script **on both seed variants before hashing/uploading** the same PE files that the real Windows ARM64 runner later verifies and executes. The audit logs section names, raw flags, object RVAs, count of base relocations, and DLL characteristics (DYNAMIC_BASE/NX/CFG advertised bits); **logging a flag is not equivalent to independently verifying ASLR, CFG, unwind or loader relocation behavior**.

**Release boundary:** if TinyCC places encoded VM data in a writable section, omits original words in favor of another storage form, or creates relocations overlapping encoded bytes, the new strict gate fails and needs an upstream compiler/layout fix. This does not add a fallback engine or move protected data into a writable arena. The source-only encoded-string binary scan remains a distinct gate, not proof of strong encryption.
## Native Windows ARM64 loader relocation and function-table admission (W3)

`vm_upstream_static.c` now has an **actual Windows ARM64 process-time loader check**, inside the **same existing native executable**. It obtains the loaded image base from `GetModuleHandleA(NULL)`, reads the original preferred `IMAGE_OPTIONAL_HEADER64.ImageBase`, and **rejects a preferred-base load**: PE `DYNAMIC_BASE` presence alone is insufficient. It opens the current image file, traverses its base relocation table and checks every supported DIR64 record by comparing the original on-disk 64-bit word with the live image word plus the *observed* load-base delta. Unknown relocation kinds, malformed blocks, unmapped RVA targets, or any mismatch fail closed; this is evidence of the Windows loader actually applying relocation records, not merely their existence in `.reloc`.

The same live image check calls `VirtualQuery` on two known source-format static bytecode arrays to require **committed `PAGE_READONLY` memory**; the earlier cross-build PE parser independently verifies their `R`/not-`W`/not-`X` section placement and relocation non-overlap. It looks up the nonleaf VM differential routine using the real Windows `RtlLookupFunctionEntry` API and verifies the loader-returned function-table entry is **within the current image's `.pdata` exception directory** and reports this image's base. This tests real Windows function-table registration, **not** unwinding through an exception.

The unchanged `windows-arm64-native` job runs the existing static VM executable **10 times per seed** and requires one explicit `ARM64_NATIVE_LOADER_RELOC_PDATA_PASS` receipt on every execution, with a nonzero relocation delta and at least one verified DIR64 relocation. All other original smoke/VM/nonce/string programs still run ten times; there is no new workflow, SDK installer/consumer project, runtime engine or fallback.

**Release boundary:** loader relocation applied at nonpreferred base and successful `.pdata` lookup are distinct from **actual stack unwinding/SEH exception propagation** and CFG target enforcement. The current TinyCC PE did **not advertise `GUARD_CF`** in the earlier inspection; a successful function-table lookup cannot be misreported as CFG. External calling ABI and full protected original `HIDE_STRING`/CFLOW/stack proxies remain open.

## Next architectural gates

1. Define `obfus.h` architecture dispatch at its existing section boundaries, preserving unchanged x86/x64 behavior; separate portable entropy/string/VM semantics from ISA-specific code. Upstream remains unmodified until a qualified patch exists.
2. Implement ARM64 stack-/branch-proxy prototypes with genuine A64 encodings and compiler clobber constraints. No SP/LR modifications, no writable-executable sections, no executable junk or skipped-byte gadgets in the first pass; require unwinder correctness before changing frame layout.
3. Prove Windows ARM64 unwind/exception/CFG and BTI/PAC compatibility when relevant, and build *real* differential tests against a no-obfuscation baseline. Reject unsupported options with compile-time errors instead of pretending success.
4. Only then qualify an opt-in TCC `obfus.h` ARM64 distribution; ARM32 and non-Windows deployment require separate work.
